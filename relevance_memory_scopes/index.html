DLBacktrace Relevance Memory Management¶

Quick Answer: Are all relevances saved in float16?¶

YES ✅ — By default, all relevance tensors are converted to float16 regardless of the cache policy chosen ("full", "summary", or "disk").

Why this happens:¶

  1. Default parameter in dlb_auto_sampler.py line 381: 

    relevance_compress_dtype: Optional[Any] = "float16"  # ← Default value

  2. Universal compression in _store_relevance_entry() line 320: 

    # ALL policies go through this compression step first
processed = self._compress_relevance_tree(
    rel_dict, 
    target_dtype=target_dtype,  # ← float16 by default
    move_to_cpu=move_to_cpu
)

  3. Policy-agnostic implementation:

  4. ✅ policy="full" → Returns compressed tree
  5. ✅ policy="summary" → Summarizes compressed tree
  6. ✅ policy="disk" → Saves compressed tree to disk
  7. ❌ policy="none" → Skips compression (returns None)

To change this behavior:¶

# Option 1: Disable compression (keep float32)
relevance_compress_dtype=None

# Option 2: Use different precision
relevance_compress_dtype="float32"   # Full precision (2x memory)
relevance_compress_dtype="bfloat16"  # Better range than float16

# Option 3: Use torch.dtype directly
relevance_compress_dtype=torch.float16

Memory impact:¶

  • float32 → float16: 50% reduction (4 bytes → 2 bytes per element)
  • Example: 10 tokens × 34 MB/token = 340 MB (float16) vs 680 MB (float32)

Current Implementation¶

⚠️ Critical Finding: Float16 Conversion Applies to ALL Policies¶

YES, all relevances are saved in float16 format by default, regardless of the policy chosen. This is controlled by:

# From dlb_auto_sampler.py line 381
relevance_compress_dtype: Optional[Any] = "float16",  # Default parameter

How it works:

  1. Entry point (_store_relevance_entry()):
  2. ALL policies except "none" call _compress_relevance_tree() first

  3. The target_dtype parameter is ALWAYS passed through

  4. Compression logic (_compress_relevance_tree() line 280-294): 

    def _compress_relevance_tree(self, data, *, target_dtype=None, move_to_cpu=True):
    if torch.is_tensor(data):
        tensor = data.detach()
        if move_to_cpu:
            tensor = tensor.to("cpu")          # ← CPU offload
        if target_dtype is not None:
            tensor = tensor.to(dtype=target_dtype)  # ← DTYPE CONVERSION
        return tensor.clone()
    # Recursively processes dicts, lists, tuples...

  5. Applied to all policies:

  6. ✅ policy="full": Compressed tree returned directly
  7. ✅ policy="summary": Tree compressed before summarization
  8. ✅ policy="disk": Compressed tree saved to disk
  9. ❌ policy="none": No processing, returns None

To disable float16 compression: 

relevance_compress_dtype=None  # Keep original dtype (usually float32)

To use different precision: 

relevance_compress_dtype="bfloat16"  # Brain float16 (better range)
relevance_compress_dtype="float32"   # Full precision (2x memory)
relevance_compress_dtype=torch.float16  # Also accepts torch.dtype

See PyTorch dtype documentation: Tensor Attributes

Cache Policy Architecture¶

DLBacktrace implements a four-tier caching system for relevance data in dl_backtrace/pytorch_backtrace/dlbacktrace/core/dlb_auto_sampler.py:

1. policy="full" (Default)¶

relevance_cache_policy="full"
relevance_compress_dtype="float16"  # Target dtype for compression
relevance_move_to_cpu=True          # Move to CPU memory

What gets stored per generation step: - Complete relevance dictionary for all graph nodes - Applies dtype conversion (float16 by default) - Moves tensors to CPU if relevance_move_to_cpu=True - Returns: Full nested dict structure with all tensors

Implementation: _store_relevance_entry() → _compress_relevance_tree()

2. policy="summary"¶

relevance_cache_policy="summary"

What gets stored per generation step: - Single scalar value (sum of all relevance tensors) - Memory-efficient for tracking relevance magnitude trends - Returns: {"summary": <float>}

Implementation: Calls _summarize_relevance() which recursively sums all tensors

3. policy="disk"¶

relevance_cache_policy="disk"
relevance_cache_dir="./relevance_cache"  # REQUIRED
relevance_compress_dtype="float16"
relevance_move_to_cpu=True
relevance_use_compression=True  # NEW: Enable pickle protocol 4 compression (default: True)
relevance_pickle_protocol=4     # NEW: Pickle protocol 2-5 (default: 4)

What gets stored per generation step: - Compressed .pt file with full relevance tree (e.g., step_00000.pt) - Uses PyTorch's optimized pickle protocol 4+ for better compression - ZIP64 serialization format for large tensors (PyTorch 1.6+) - Only summary + file path kept in RAM - Returns: {"summary": <float>, "path": "/path/to/step_00000.pt"}

Compression Benefits: - Pickle Protocol 4: 20-30% smaller files vs default protocol 2 - Pickle Protocol 5: Best compression, requires Python 3.8+ - ZIP64 Format: Efficient storage for large tensor archives - Combined with float16: 50-60% total reduction vs float32 + protocol 2

Implementation: Calls torch.save() with pickle_protocol=4 and _use_new_zipfile_serialization=True

What gets stored per generation step: - Full relevance dict saved to disk as step_XXXXX.pt files - Keeps only summary scalar + file path in memory - Uses torch.save() with default zipfile serialization - Returns: {"summary": <float>, "path": "<filepath>"}

Implementation: Saves compressed tree to disk, returns metadata

4. policy="none"¶

relevance_cache_policy="none"

What gets stored: - Nothing. Relevance computation is skipped entirely. - Returns: None

Memory Footprint Analysis¶

Why "full" Policy Still Uses ~14GB¶

Based on investigation of dl_backtrace/pytorch_backtrace/dlbacktrace/core/dlb_auto_sampler.py:

Root Cause: The "full" policy DOES apply compression, but the compressed data is still large because:

  1. Vocabulary Size Factor
  2. Models like Qwen3-4B have vocab size ~151,936
  3. Each generation step stores relevance for every layer's output

  4. Example: For a model with 32 layers, each step stores 32+ tensors

  5. What Gets Stored (Per Token) 

    # Example relevance dict structure:
{
    'input_ids': np.ndarray(shape=[batch, seq_len], dtype=float16),  # Input relevance
    'layer_0_output': np.ndarray(shape=[batch, seq_len, hidden_dim], dtype=float16),
    'layer_1_output': np.ndarray(shape=[batch, seq_len, hidden_dim], dtype=float16),
    # ... 30+ more layers
    'output': np.ndarray(shape=[batch, seq_len, vocab_size], dtype=float16),  # ~300MB alone!
}

  6. Memory Calculation (Qwen3-4B, 10 tokens)

  7. Vocab size: 151,936
  8. Hidden dim: 3,584
  9. Sequence length: 64 (average)
  10. Layers: 32

Per generation step: 

Output layer relevance: 1 × 64 × 151,936 × 2 bytes = ~18.5 MB
Hidden layers (32×): 1 × 64 × 3,584 × 32 × 2 bytes = ~14.7 MB  
Input/embeddings: ~1 MB
------------------------------------------------------------
Total per step: ~34 MB (compressed to float16)

For 10 tokens: 34 MB × 10 = ~340 MB
For 290 samples: 340 MB × 290 = ~98.6 GB

  1. Compression IS Applied 

    # From _compress_relevance_tree()
if torch.is_tensor(data):
    tensor = data.detach()
    if move_to_cpu:
        tensor = tensor.to("cpu")            # ✓ CPU offload
    if target_dtype is not None:
        tensor = tensor.to(dtype=target_dtype)  # ✓ float16 conversion
    return tensor.clone()

  2. Why Still Large

  3. float16 is 50% smaller than float32, but still 2 bytes per element
  4. No structural compression (quantization, sparsification, pruning)
  5. Every intermediate layer output preserved
  6. Full vocabulary relevance stored even for single predicted token

Compression Techniques¶

Currently Implemented ✅¶

Technique Implementation Memory Savings Applies To Location
CPU Offload tensor.to("cpu") Frees VRAM → host RAM All policies _compress_relevance_tree() line 284
Dtype Conversion .to(dtype=torch.float16) 50% reduction (fp32→fp16) All policies (default) _compress_relevance_tree() line 286
Pickle Protocol 4+ torch.save(..., pickle_protocol=4) 20-30% additional policy="disk" only _store_relevance_entry() line 347
ZIP64 Format _use_new_zipfile_serialization=True Included in protocol 4+ policy="disk" only _store_relevance_entry() line 349
Lazy Disk Storage torch.save(data, path) Keeps only summary in RAM policy="disk" only _store_relevance_entry() line 332
Scalar Summaries Recursive tensor summation 99.99%+ reduction policy="summary" only _summarize_relevance() line 240

Key Insight: The float16 conversion at line 286 is executed for ALL policies except "none", because _compress_relevance_tree() is called first in _store_relevance_entry() (line 320) before policy-specific branching.

Cache Policy Guide¶

Dtype Precision Control¶

Default behavior: All policies apply float16 compression automatically.

Scenario Recommended Config Memory Precision
Production (most cases) relevance_compress_dtype="float16" Baseline Good
High precision needed relevance_compress_dtype="float32" 2x memory Best
Memory-constrained relevance_compress_dtype="float16" + policy="disk" Minimal RAM Good
Research/debugging relevance_compress_dtype="bfloat16" Baseline Better range
No compression relevance_compress_dtype=None 2x memory Best

Important: Even policy="summary" applies dtype conversion before summarization. To get true float32 summaries: 

relevance_cache_policy="summary"
relevance_compress_dtype=None  # ← Prevents conversion

Decision Tree: Which Policy to Use?¶

Do you need per-layer relevance data?
├─ No → Use policy="summary" (99.9% memory savings)
│
├─ Yes → Do you need it during generation?
   ├─ No → Use policy="disk" (RAM stays constant)
   │
   └─ Yes → How much RAM/VRAM do you have?
      ├─ <32GB → Use policy="disk" + float16
      ├─ 32-128GB → Use policy="full" + float16 (default)
      └─ >128GB → Use policy="full" + float32 (high precision)

Experimental Features (Not Documented in Public API)¶

Hybrid Formats¶

Combine PyTorch tensors for hot-path compute with NumPy arrays for archival storage:

# Convert to NumPy for analysis
relevance_np = {
    k: v.detach().cpu().numpy() if torch.is_tensor(v) else v
    for k, v in relevance_dict.items()
}

# Save with NumPy compression
np.savez_compressed("relevance_step_0.npz", **relevance_np)

Memory-Mapped Access¶

For datasets too large for RAM:

# Save individual tensors
for key, tensor in relevance_dict.items():
    np.save(f"relevance_{key}.npy", tensor.numpy())

# Load as memmap (no RAM allocation)
relevance_memmap = {
    key: np.load(f"relevance_{key}.npy", mmap_mode='r')
    for key in relevance_dict.keys()
}
