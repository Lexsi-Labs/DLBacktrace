Relevance Memory Optimization Plan¶

Objectives¶

  • Reduce peak memory used while collecting relevance traces during text generation via run_task() / DLBAutoSampler.generate().
  • Preserve the ability to inspect per-node relevance when explicitly requested, without forcing users to keep every tensor resident on GPU/CPU RAM.
  • Keep run_task() API backward-compatible for existing notebooks such as cuda_llama_3_2_1B_run_task.ipynb.

Key References To Inspect¶

  1. dl_backtrace/pytorch_backtrace/dlbacktrace/core/dlb_auto_sampler.py (focus on generate() paths for sampling vs. beam search, plus _compute_relevance).
  2. dl_backtrace/pytorch_backtrace/dlbacktrace/dlbacktrace.py (run_task() plumbing for return_relevance, return_layerwise_output, return_scores).
  3. Notebook cuda_llama_3_2_1B_run_task.ipynb to understand how run_task() outputs are consumed in practice.
  4. Repository documentation via mcp_docs-mcp_describe_tenant to capture any existing guidance on trace storage expectations.
  5. semantic_search over dl_backtrace/pytorch_backtrace to locate other consumers of relevance_trace / all_wt that must stay compatible.

Investigation Steps¶

  1. Run semantic search for relevance_trace, relevance_data, all_wt, and relevance storage patterns across pytorch_backtrace to gauge scope.
  2. Review notebook usage to see which fields are actually plotted/visualized and whether entire dictionaries are required, or summaries suffice.
  3. Trace data shape audit within DLBAutoSampler.generate() for both sampling and beam paths to pinpoint where 14 GB arises (tensor dtype, device placement, duplication per step).
  4. Check evaluation outputs (self.dlb.evaluation) to determine minimal data needed for downstream metrics/visualizations.
  5. Consult docs via mcp_docs-mcp_describe_tenant for any constraints on how relevance data should be serialized or summarized.

Design Exploration¶

  • Lazy / streaming storage: move per-token relevance dicts to disk (JSON or npz) or expose iterator; keep only per-token summaries in-memory by default. Can we use any compression way to do it. Give more emphasize on it.
  • Selective retention: allow callers to specify relevance_cache_policy (e.g., "none" | "summary" | "full") passed from run_task() to sample_auto()/generate().
  • Tensor compaction: detach relevance tensors to CPU float16 before storing, optionally prune near-zero entries.

Implementation Plan (Tentative)¶

  1. Add configuration knobs (e.g., relevance_store dict) to run_task() and pass through to sample_auto() / DLBAutoSampler.generate().
  2. Implement a small helper in DLBAutoSampler to compress or offload relevance dicts (CPU move, dtype_CAST, pruning, summary-only mode).
  3. Ensure beam + sampling paths share the same helper to avoid duplication.
  4. Update notebook (if needed) to demonstrate new options and verify memory savings.
  5. Extend tests or add a lightweight script confirming that relevance summaries still match existing visualizations when full mode is enabled.
  6. Check for any compression way for memory optimization. So that memory to store the layerwise relevance should be as minimum as possible.

Validation¶

  • Measure peak memory before/after with a representative prompt (seq=64, next 5 tokens) to confirm substantial reduction.
  • Run notebook cuda_llama_3_2_1B_run_task.ipynb (or a smaller mock) to ensure outputs consumed by visualization helpers remain intact.
  • Document new knobs in README/docs to keep API clarity.

Investigation Results Summary (December 17, 2025)¶

✅ Confirmed: Float16 Compression Applied to ALL Policies¶

Question: Are all relevances being saved in float16 format regardless of policy chosen?

Answer: YES ✅

Evidence:¶

  1. Code Location: dl_backtrace/pytorch_backtrace/dlbacktrace/core/dlb_auto_sampler.py
  2. Line 381: relevance_compress_dtype: Optional[Any] = "float16" (default parameter)
  3. Line 320: ALL policies call _compress_relevance_tree() before policy-specific logic

  4. Line 286: dtype conversion applied unconditionally if target_dtype is not None

  5. Implementation Flow: 

    _store_relevance_entry() [line 307]
├─ Line 320: processed = _compress_relevance_tree(rel_dict, target_dtype=cache_dtype, ...)
│  └─ Line 286: tensor.to(dtype=target_dtype)  # ← ALWAYS EXECUTED
├─ Line 324: if policy == "summary" → return summary of COMPRESSED tree
├─ Line 327: if policy == "disk" → save COMPRESSED tree to disk
└─ Line 341: if policy == "full" → return COMPRESSED tree

  6. Applies To:

  7. ✅ policy="full" — compressed tree returned
  8. ✅ policy="summary" — compressed tree summarized
  9. ✅ policy="disk" — compressed tree saved

  10. ❌ policy="none" — no processing

  11. Memory Impact:

  12. With compression (default): ~340 MB per sample (10 tokens)
  13. Without compression: ~680 MB per sample (10 tokens)

  14. Savings: 50% reduction

  15. To Override: 

    # Keep float32 precision
relevance_compress_dtype=None

# Use different precision
relevance_compress_dtype="bfloat16"  # Better range
relevance_compress_dtype="float32"   # Full precision (2x memory)

Documentation Updated:¶

  • ✅ Added critical finding section to relevance_memory_scopes.md
  • ✅ Updated compression techniques table with "Applies To" column
  • ✅ Added dtype precision control section
  • ✅ Created verification script: docs/examples/verify_dtype_compression.py
  • ✅ Added PyTorch documentation references for tensor.to() behavior

Key Takeaway:¶

The 14GB storage per sample is NOT due to missing compression—compression IS working. The data is simply massive even after 50% reduction because: - Vocabulary size: 151,936 tokens - 32+ layers with hidden dim 3,584 - Full relevance stored for every layer, every token

Recommendation: Use policy="disk" to keep RAM constant while still benefiting from float16 compression on disk.

Phase 2: Comprehensive Storage Optimization Plan¶

📋 See: Relevance Storage Optimization Plan

Problem Statement¶

  • Current storage: 2.75 GB per token × 5 tokens = 13.75 GB per sample
  • Root cause: Storing ALL computation graph nodes per generation step
  • Constraint: Must maintain node-level granularity for full LRP attribution

Optimization Strategies¶

A comprehensive plan has been developed with multiple complementary techniques:

1. Sparse Tensor Compression (PyTorch CSR/COO)¶

  • Reduction: 20-100x for >90% sparse matrices
  • Implementation: Convert to torch.sparse_csr after threshold pruning
  • Trade-off: CPU-only operations (PyTorch 2.9)

2. Top-K Vocabulary Pruning¶

  • Reduction: 484x by keeping only top-100 tokens per position
  • Implementation: torch.topk() on vocabulary dimension
  • Use case: Most interpretability needs <100 tokens

3. Hierarchical Layer Sampling¶

  • Reduction: 32,000x by storing full data only for critical layers
  • Strategy: Full storage for layers [0, mid, -1], summaries for others
  • Benefit: Preserves end-to-end attribution path

4. Int8 Quantization¶

  • Reduction: Additional 2x on top of float16
  • Accuracy: <1% relative error, preserves ranking
  • Implementation: Dynamic quantization with scale/zero_point

5. Zstandard Compression¶

  • Reduction: 3-5x additional for disk storage
  • Latency: <100ms decompression per step
  • Better than gzip: Optimized for tensor data patterns

Expected Results¶

Implementation Roadmap¶

Week 1-2: Quick wins (10-50x reduction) - Top-K pruning (k=100) - Threshold-based sparsification (>90% zeros) - Zstandard compression on disk writes

Week 5-6: Production optimization - Memory-mapped lazy loading - Configuration presets (quality/balanced/minimal) - Validation suite for quality preservation
