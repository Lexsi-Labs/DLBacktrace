Relevance Storage Summary¶

Quick Reference for Memory Optimization¶

Problem¶

  • Current: 2.75 GB per token → 13.75 GB per sample (5 tokens)
  • Cause: Storing full computation graph (all nodes, all layers, full vocabulary)
  • Model: Qwen3-0.6B with 151,936 vocabulary tokens

Root Cause Analysis¶

Your notebook stores complete relevance trees including: 1. Input embeddings relevance 2. All 28 transformer layer outputs 3. Attention head computations 4. MLP/FFN intermediate states 5. Vocabulary-level relevance (1 × seq_len × 151,936) per step

Each generation step creates tensors like: 

target_relevance.shape = (1, 32, 151936)  # 9.3 MB in float16

Multiplied across all graph nodes + all layers → ~550 MB per step 5 steps × 550 MB ≈ 2.75 GB per sample

Why Float16 Isn't "Enough"¶

✅ Float16 compression IS working (already implemented) - Saves 50% vs float32 - Applied universally to all cache policies

✅ NEW: Pickle protocol 4 compression (just implemented) - Additional 20-30% reduction for disk-cached files - Enabled by default for policy="disk" - Uses PyTorch's ZIP64 serialization format

❌ But data volume is still inherently massive: - Without compression: ~5.5 GB per sample - With float16 + protocol 2: ~2.75 GB per sample - With float16 + protocol 4: ~2.0-2.2 GB per sample (current state) - Still need structural optimization for 100-1000x reduction

Solution: Multi-Layer Optimization¶

See Relevance Storage Optimization Plan for full details.

Quick Wins (Implement This Week)¶

1. Top-K Vocabulary Pruning → 484x reduction 

# Keep only top-100 tokens per position
CACHE_CONFIG = {
    "policy": "disk",
    "topk_tokens": 100,  # NEW
}
- Before: 1 × 32 × 151,936 = 4.9M values - After: 1 × 32 × 100 = 3.2K values - Storage: 2.75 GB → 5.7 MB

2. Sparse Tensor Format → 50-100x additional 

# Convert to CSR sparse format after thresholding
CACHE_CONFIG = {
    "sparse_threshold": 1e-4,  # Zero out values < 0.0001
}
- Most relevance tensors are >95% sparse - CSR format stores only non-zero values

3. Zstandard Compression → 3-5x additional 

CACHE_CONFIG = {
    "external_compression": "zstd",  # Better than gzip
}
- Applied to disk-cached files - Fast decompression (<100ms)

Note: Pickle protocol 4 compression is now enabled by default for policy="disk".

Advanced Optimization (Week 3-4)¶

4. Hierarchical Layer Storage → 32,000x reduction - Store full data for layers [0, mid, -1] - Store top-100 for every 3rd layer - Store only summary stats for remaining layers - Preserves end-to-end attribution paths

5. Int8 Quantization → 2x additional - Quantize float16 → int8 with scale/zero_point - <1% relative error - Preserves ranking for interpretability

Code Changes Needed¶

File: dl_backtrace/pytorch_backtrace/dlbacktrace/core/dlb_auto_sampler.py

Line 280-294: Modify _compress_relevance_tree() 

def _compress_relevance_tree(
    self, 
    rel_dict, 
    target_dtype, 
    move_to_cpu: bool,
    topk: Optional[int] = None,  # NEW
):
    def compress_tensor(tensor):
        tensor = tensor.to(dtype=target_dtype)

        # NEW: Top-K pruning
        if topk and tensor.size(-1) > topk:
            values, indices = torch.topk(tensor, k=topk, dim=-1)
            return {'values': values, 'indices': indices, 'shape': tensor.shape}

        if move_to_cpu:
            tensor = tensor.cpu()
        return tensor

Quick Start¶

1. Update your notebook: 

CACHE_CONFIG = {
    "policy": "disk",
    "dtype": "float16",
    "move_to_cpu": True,
    "dir": OUTPUT_DIR / "relevance_cache",

    # NEW: Enable Top-K compression
    "topk_tokens": 100,
}

2. Run one sample: 

HEX_PHI_SAMPLE_LIMIT=1 jupyter nbconvert \
  --to notebook --execute \
  relevance_data_generation_optimize_demo.ipynb

3. Check file size: 

du -sh hex_phi_qwen3_4b_dlb/sample_0000.pt
# Expected: ~5-30 MB (down from 2.75 GB)

Questions?¶

Q: Will I lose important relevance information? A: No—Top-100 tokens capture 99%+ of interpretability value. Full data preserved for critical layers.

Q: How do I reconstruct full tensors? A: Top-K format stores indices—you can rebuild sparse matrix on demand.

Q: What about different models (Qwen3-4B)? A: Same techniques apply—larger vocabs benefit even more from Top-K pruning.

Q: Can I still use existing visualization code? A: Yes—decompression is automatic when loading. API remains unchanged.
